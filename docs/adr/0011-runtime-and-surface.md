# 0011. Runtime and surface: generated operations on a hand-written runtime

Status: accepted, 2026-10-03. Supersedes the "thin per-operation methods are
handwritten" part of ADR 0002; the rest of ADR 0002 stands.

## Context

The platform decided (RFC 0020, 2026-10-02) that the SDK a developer generates has
exactly the operations their credential may call: the gateway serves each credential
its own OpenAPI document, cut by the account's plan and the credential's scopes, and
`iohr sdk generate` turns that document into code in the developer's repository, for
one account or several at once, checked by the compiler where the language allows.

ADR 0002 planned one published SDK per language with hand-written per-operation
methods. Two SDKs per language, one published with every operation and one generated
per developer with a subset, would be two codebases to keep equal. And a published
crate with no operations at all would be a poor first experience: `cargo add inorbithr`
should work out of the box.

## Decision

1. **Each language has one runtime and many surfaces.** The runtime is published once
   per language and hand-written: client, configuration, token handling, retries,
   errors, hooks, later streaming. It holds no operation. A surface is generated: the
   models and the thin operation methods for a set of operations, calling the runtime's
   low-level request path.
2. **The published package carries the public surface, generated by the same
   generator.** `rust/src/generated/` is written by `iohr sdk generate` from
   `spec/openapi.json` (the public document, every scope) and committed; CI regenerates
   it and fails on a diff. So `inorbithr::Client` calls the public API as it is, the
   generator is exercised on every spec sync, and a developer's generated surface is
   the same code for fewer operations.
3. **The runtime's contract with generated code is explicit.** `Operation` is the one
   way a surface reaches the transport; `__codegen::VERSION` is asserted by every
   generated file at compile time and bumped when an older surface would no longer
   compile or behave the same.
4. **Profiles are types.** `Client<P: Profile>` is generic over a zero-sized profile
   type; a generated surface implements each operation's marker trait for the profiles
   whose cut holds it, through handle types local to the surface (a developer's crate
   cannot add inherent methods to `Client`). `Public` is the profile of the published
   surface. Credentials are read from `INORBIT_<PROFILE>_*` with no fallback to the
   bare names, so a named profile's client calls its own account or nothing.
5. **The error codes are the platform's.** `Code` has the 17 slugs of `spec/problem.json`
   plus an `Unknown` fallback that keeps the raw slug. The command line's private client
   had used other names for three of them (`invalid_argument`, `permission_denied`,
   `deadline_exceeded`); the platform's win.
6. **The runtimes arrive one language at a time.** Rust first, because the generator's
   model and its first target are settled against it; TypeScript, Python, Go, Java and
   C# follow, each released when it passes the whole conformance suite. The parity rule
   in `AGENTS.md` ("every public change lands in all four languages") applies to a
   change of behaviour or surface, and a case a runtime does not pass yet is `pending`
   for that language, never weakened.
7. **The generator crates live in `cli/`** (`iohr-openapi`, `iohr-codegen`), beside the
   command line that runs them, so a developer needs one binary and no other toolchain.
   The `rust` CI job watches them too.
8. **The command line uses the runtime.** Once the Rust runtime exists, the command line
   depends on `inorbithr` by path and drops its private client, as ADR 0009 said; its
   `Credential` becomes a `TokenProvider`.

## Consequences

- `rust/` is a package of its own, `publish = false` until the public surface is
  generated into it and M4 declares the first release; the `release-crates`
  environment also waits for a maintainer, so nothing half-built reaches crates.io.
- `docs/design.md` gains a section on the split; section 1's operation table describes
  the public surface, which is one of many.
- The conformance driver runs the cases through the generated public surface, so a
  passing suite proves the generated code, not a hand-written copy of it.
- `rust/Cargo.lock` and, once the command line depends on the crate, `cli/Cargo.lock`
  carry the crate's version; release-please updates them (`extra-files`), and a release
  that leaves one stale fails `--locked` in CI and is fixed before it ships.
